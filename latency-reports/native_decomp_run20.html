What this test does

testperplatencyv1's native-transfer test sends real SOL transfers back and forth between two wallets, over and over, alternating direction each time: Wallet 1 (the bot's own fee-paying wallet, which also covers every transaction's network fee and priority fee regardless of which direction the transfer goes) and Wallet 2 (a second wallet, deterministically derived from Wallet 1, used purely as a round-trip destination -- it never pays a fee in either direction).

Each transfer races three independent, real update channels to see which one reports the transfer's confirmation first: Account (processed-tier balance update, fastest), Commit (rooted-tier, ~32 slots behind live), and Transaction (direct signature confirmation).

The landing slot's own pipeline, decomposed

Every Solana slot passes through real, distinct stages on this validator, each with its own SlotStatus notification from the actual Agave geyser plugin -- not something this guest infers or estimates:

  • FirstShredReceived -- the first real network shred (Turbine) for this slot arrives here.
  • Completed -- every shred for the slot has arrived; the block is fully assembled locally.
  • Processed -- this validator has locally replayed the block -- its own local replay, unrelated to leader timing.
  • Confirmed -- real cluster-wide supermajority vote acknowledgment.

Write is measured against FirstShredReceived -- the earliest evidence this guest (a downstream validator, not the leader) ever gets that the leader saw/included the transfer. Read is everything after that: the rest of block delivery, this validator's own local replay, cluster confirmation, and this guest's own dispatch overhead, all the way until the winning lane noticed. Shred→Completed, Completed→Processed, and Processed→Confirmed are reported alongside as real, independent, informational sub-stages of what's inside that Read window -- not subtracted from anything.

Fifth full run -- 20/20 landed in ~38 seconds, and this is the first run with the auto-sweep fix: at completion the guest automatically queued a single transaction sending both test wallets' remaining SOL back to the real parent wallet (219,110,985 lamports: 211,121,085 from owner + 8,000,000 from wallet2, less a 10,100 lamport fee reserve) -- confirmed on-chain, no manual recovery needed this time. All 20 via Astralane, all 20 won by Account/LowLatency. Note: `slots until inclusion` ran higher than usual this run (p50 5, p99 8, vs. the usual p50 1) -- a real, measured effect of catching up after the boot funding transfer's own delay, not a measurement artifact.
Write is a lower bound, Read is an upper bound. Neither the account-update stream nor the transaction-confirmation stream carries a timestamp for exactly when inside a landing slot's block a transfer executed -- only the slot number. "Write" is measured against FirstShredReceived, not the transfer's real execution instant, so the true write time can run later than what's shown -- see the three columns below for real, measured evidence of exactly how much later. Because Read is derived as Total − Write, an understated Write correspondingly overstates Read by the same margin.

Dotted/dashed values are estimates, not measurements. A same-slot sample has no resolvable Write/Read split at all -- shown with a ~dotted underline when a real upper bound exists (the estimate is that bound's midpoint), or a fainter ~dashed underline when even that bound is unavailable (falls back to this run's own median resolved Write delay). Hover either for the exact reasoning.

shred→completed / completed→processed / processed→confirmed are independent, supplementary stats -- never subtracted from Read. They describe what happens to the landing slot on this validator, regardless of when this guest's own winning lane happened to notice the transfer. processed→confirmed in particular is often blank: cluster confirmation frequently hasn't happened yet by the time the Account lane already has its answer, since that lane only needs local Processed state, not cluster consensus.

How each portion of the cycle is calculated

Every value below comes from real, directly-measured wall-clock Instants -- either this guest's own send-time clock, or a per-slot timestamp recorded the first time this guest sees a given SlotStatus notification for that slot (real Agave validator geyser events, not estimated -- see the section above). Nothing here is derived from an assumed slot-time constant.

MetricFormulaReal inputs used
Total sent_at.elapsed() This guest's own send `Instant` vs. the moment the winning lane (Account/Commit/Transaction) claimed the transfer. Always real and exact.
Write ≥ FirstShredReceived(inclusion_slot) − sent_at This guest's own send `Instant`; the first time it saw SlotStatus::FirstShredReceived for the real landing slot. A lower bound -- the transfer's real execution instant inside that slot's block can only be later.
Read ≤ Total − Write Derived, not separately measured -- inherits Write's understatement as an equal overstatement. `None` whenever Write is `None` (same-slot samples), never derived as `Total − 0`.
Shred→Completed Completed(inclusion_slot) − FirstShredReceived(inclusion_slot) Two real per-slot timestamps on this validator. Independent stat -- not part of Write/Read at all.
Completed→Processed Processed(inclusion_slot) − Completed(inclusion_slot) Same two-timestamp pattern -- this validator's own local replay time once the block was fully assembled.
Processed→Confirmed Confirmed(inclusion_slot) − Processed(inclusion_slot) Same pattern again. Frequently unresolved: Confirmed often hasn't fired yet by the time this sample is recorded, since the winning lane usually only needs local Processed state.
Write ≥ (estimated, dotted) write_bound_us / 2 Only for same-slot samples with a real upper bound (the first-observed Instant for any slot after inclusion_slot). Midpoint guess between 0 and that bound -- not a measurement.
Write ≥ (estimated, dashed) median of this run's real resolved Write values Only when even the upper bound above is unavailable. A rough prior, not tied to this specific sample.

All six timestamp inputs (send, FirstShredReceived, Completed, Processed, Confirmed, and the winning lane's own observation instant) come from the same per-slot record (SlotTimestamps), each field set once, the first time this guest sees that specific status for that slot number.
