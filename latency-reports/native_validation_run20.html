What this test does

testperplatencyv1's native-transfer test sends real SOL transfers back and forth between two wallets, over and over, alternating direction each time: Wallet 1 (the bot's own fee-paying wallet, which also covers every transaction's network fee and priority fee regardless of which direction the transfer goes) and Wallet 2 (a second wallet, deterministically derived from Wallet 1, used purely as a round-trip destination -- it never pays a fee in either direction).

Each transfer races three independent, real update channels to see which one reports the transfer's confirmation first:

  • Account (internally LowLatency) -- a processed-tier account-balance update, the fastest tier Solana exposes.
  • Commit -- a rooted-tier account-balance update, structurally ~32 slots (finality) behind live.
  • Transaction -- a direct signature-confirmation, independent of either account-balance stream.

Whichever lane observes the expected balance change (or the expected transaction landing) first wins and gets timed. For each confirmed transfer, the test also tries to split total latency into write (time from send until the transfer actually landed on-chain) and read (time from landing until this guest's own update stream reported it) -- see the caveat box below for exactly what that split can and can't promise.

Clean sweep: 20/20 via Account, all Astralane-bundled. Every transfer this run -- both directions -- landed within 0-2 slots and was confirmed by the Account (LowLatency) lane before Commit or Transaction ever got a chance. No lane-vs-recipient lockout of any kind: the fee-math fix means a Wallet-1-recipient transfer's exact-match threshold is reachable now, and Astralane's tip-boosted landing means it usually resolves before Commit's ~32-slot rooted lag or Transaction's independent confirmation even arrive.
Write is a lower bound, Read is an upper bound. Neither the account-update stream nor the transaction-confirmation stream carries a timestamp for exactly when inside a landing slot's block a transfer executed -- only the slot number. "Write" is measured against the first moment this guest observed the landing slot beginning, not the transfer's real execution instant, so the true write time can run up to roughly one Solana slot later (currently ~350ms, and shrinking) than what's shown. Because Read is derived as Total − Write, an understated Write correspondingly overstates Read by the same margin. This is a real measurement-resolution limit of the data available, not a bug -- treat single-sample Write/Read splits as directional, not exact, especially anywhere close to that ~350ms band.

Dotted/dashed values are estimates, not measurements. A same-slot sample has no resolvable Write/Read split at all -- shown with a ~dotted underline when a real upper bound exists (the estimate is that bound's midpoint -- the true value could be anywhere from 0 up to the bound, this is just a guess at the middle), or a fainter ~dashed underline when even that bound is unavailable (falls back to this run's own median resolved Write delay -- a much rougher prior, not tied to this specific sample at all). Investigation: transfers 4 and 7, write/read outliers in opposite directions

Transfer 7 attributed almost all of its latency to write (326,431µs) with read near zero (4,290µs). Transfer 4 was the mirror image: write near zero (46µs), read dominant (705,714µs). Neither is a bug -- they're the write/read split correctly capturing two genuinely independent sub-latencies that happened to land at opposite extremes.

Transfer 7 — write dominates, read ≈ 0

[20.779s] sending 1,000,000 lamports Wallet 1 -> Wallet 2, sent_at ≈ 20.779s, send_slot=443989546
[21.110s] on_account pubkey 203922733 (Wallet 1); slot 443989547        <- separate account, same tick
[21.110s] confirmed via LowLatency  write=326,431µs  read=4,290µs  total=330,722µs
[21.110s] on_account pubkey 122477695 (Wallet 2); slot 443989547        <- the actual matching update

Nothing else is logged between 20.983s and 21.110s -- a genuine ~127ms gap where the guest is just idle, waiting on the next message from the host. write_delay is instant_for_slot(547) - sent_at -- the moment the guest's own slot_clock first recorded seeing evidence of slot 547 at all. read_delay is however much longer it took after that for the specific Wallet 2 balance-match to show up. Here, both things -- "slot 547 exists" and "Wallet 2's balance now matches" -- arrived in the same delivery batch, ~4ms apart. So virtually all of the real 330ms is genuinely attributable to write: the time for slot 547 itself to be produced, propagated, and reach this guest's subscription pipeline at all. Once it arrived, the answer was already sitting right there.

Speculation on cause: nothing algorithmic -- instant_for_slot almost certainly got an exact match here (an exact match can only be equal to or later than the true slot-547 start, never fabricated early), and the fallback-to-earlier-slot path in that function would bias write_delay down, not up, so this isn't a measurement artifact. Most likely explanation: the geyser plugin/validator batches account-write notifications for a slot together and flushes them close to (or as part of) the SlotStatus signal for that slot -- when that happens, whichever account you're watching just "rides along" with the slot notice, and read collapses to near-zero. This one landed a bit slow on the network side (326ms for one slot transition is on the high end for this run, where sub-slot times were more like 40-350ms elsewhere) -- ordinary jitter, not an anomaly.

Transfer 4 — the opposite: write ≈ 0, read dominates

[19.124s] sending 1,000,000 lamports Wallet 2 -> Wallet 1, sent_at ≈ 19.124s, send_slot=443989540
[19.585s] "578ms since previous slot's start() (target: <400ms) -- ... 8271 account/token updates ..."
[19.830s] on_account pubkey 203922733 (Wallet 1); slot 443989541
[19.830s] confirmed via LowLatency  write=46µs  read=705,714µs  total=705,760µs

Here instant_for_slot(541) resolved to essentially sent_at itself (46µs later) -- the guest already had a slot_clock entry for 541 nearly the instant the transfer was sent, meaning it had just seen that slot begin right around send time, by what's basically coincidental timing. But the specific account update for Wallet 1 (203922733) carrying the matching balance didn't show up until 706ms later -- a long, genuine propagation/delivery gap for that one account's write, well after the slot itself was already known to exist.

Speculation on cause: two real candidates, not mutually exclusive:

  • Solana-side: the validator/geyser plugin doesn't necessarily emit every account's write for a slot at the same moment -- if Wallet 1's specific write got dispatched late relative to the rest of that slot's batch (or landed as part of a later, still-processing sub-step), the guest simply wouldn't see it until that specific delivery arrives, independent of when the slot itself became visible.
  • Guest-side backpressure, with direct evidence of it right in this window: the very same window logged "578ms since previous slot's start() (target: <400ms)" -- the guest's own commit-hook cadence was running behind its 400ms target at exactly this moment, while processing 8,271 account/token updates that tick. That's a real, self-reported sign the guest's overall event-delivery pipeline was under load right when this transfer needed its answer -- plausible enough to meaningfully contribute to the delay, though not something provable as the cause versus the Solana-side explanation from the log alone.

Why this is the write/read split doing its job, not a bug: these two transfers are genuinely independent failure/success modes for two different sub-latencies -- "how long until the guest learns the landing slot exists" vs. "how long after that until the specific watched account's write actually propagates." They can and do trade off in opposite directions run to run, sample to sample, which is exactly the point of splitting them instead of reporting one blended number.
